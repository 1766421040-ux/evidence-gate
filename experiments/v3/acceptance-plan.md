# V3 独立验收方案

状态：**主任务已确认下述 seed、分组与七项门槛；冻结以同目录 protocol.json / freeze.json 为准，模型验收尚未执行**。本文只定义下一轮如何判断是否达标，不预填模型结果，也不改写 V1 / V2 已保存的失败结论。用户已授权继续优化；这是观察 V2 后的新一轮开发，原 V2 test 已见，不能再次充当独立确认集。

交付目标是让真实模型在明确的有限证据协议上通过预设验收。只有原始模型生成通过，才能写“模型达标”；规则校验、输出修补、检索后的隐藏真值或人工替换答案都不能贡献模型分数。达到本协议也不等于通过真实企业文档或生产可靠性认证。

## 1. 已知失败与本轮要防止的选模偏差

已有 [V2 选点记录](../v2/selection.json) 中，400 / 600 步的可答成功分别为 23/48 和 13/48；四动作等权严格成功率却从约 0.7677 上升到 0.7740，旧选择规则因此选中 600 步。最终 [V2 test](../v2/selected-v2.json) 只有 10/80 个可答样本成功，16 个合法 answer 中 6 个无依据。只优化一个平均分不能保证回答可用。

因此 V3 必须先检查开发集硬门槛，再在合格候选中排序。没有合格候选时保存 `no_eligible_candidate`，继续基于 train / dev 开发，不运行新 test。旧 V2 test 可以作为已见失败集用于分析；即便再次跑到高分，也只能标为回归诊断，不能用于新的确认结论。

## 2. Fresh holdout 与身份隔离

固定主数据种子 **20261029**，并对 train / dev / test 使用不同的确定性随机流域，例如 `evidence-gate-v3:20261029:dev`。先提供 80 个新 train group（1,600 行），允许在新目录扩展 train，不能改变已经冻结的 dev/test 字节。以下验收规模不随模型成绩缩减：

| 分区 | 组数 | 每组变体 | 行数 | 可答 / 非可答行数 | 用途 |
| --- | ---: | ---: | ---: | ---: | --- |
| 新 dev | 24 | 20 | 480 | 192 / 288 | 允许开发和选择候选 |
| 新 test | 60 | 20 | 1,200 | 480 / 720 | 选定且锁定后仅确认一次 |
| 可选独立 stress | 12 | 20 | 每种变换 240 | 按变换后的真值统计 | 另列压力评测 |

采用 24 / 60 组便于平衡已有三类日期组合和两种预算，也让整组成功率的一个组从旧 test 的 5 个百分点降至约 1.67 个百分点。这仍是有限合成产品组，不能按 1,200 个独立自然文档样本解释统计精度。

V2 的静态诊断还发现“三篇文档都提到所问产品”和“两篇 official 的数字相同”两个单向可答线索，故本轮不直接复刻 V2 构造。每组改为十种语义 `supported / value_changed / distractor / reordered / missing / expired / future / conflict / ambiguous / untrusted`，各有 `_b0 / _b1` 两行。每个语义的两行只改变 budget；答案充分和需要澄清时输出保持，缺失有效可信证据时按预算切换 abstain / search。

跨组采用“所有文档提到本产品的意图因子 × community 相关性因子 × 无关 official 的数字为原值/置换值/第三值”共 12 档平衡，dev 每档两组、test 每档五组。语义有必要约束：conflict 的官方值必须不同，untrusted 的 community 必须相关；不能为了表面平衡破坏标签。独立审计要求两个已知线索各自的真/假在每个 split、每个 budget 下同时具有可答与不可答反例，另列联合特征表，不宣称消灭全部捷径。

`value_changed` 只改适用官方事实的值及恢复世界中对应事实，保持无关 official 的值不变；`distractor` 只翻转 community 的语义相关性，结果仍应保持。`missing` 通过官方事实属于其他 topic 构造权威证据缺失，避免“没提产品”成为唯一线索。回答状态当前只有一篇适用 official，不覆盖多篇一致官方事实的引用集合泛化；这项边界需保留，不能写成已测试的能力。

隔离规则应由构建脚本自动核验：

1. 新 dev / test / stress 的产品、干扰产品和恢复目录实体，与 `data/main/`、`data/v2/` **全部 split** 中的实体并集，以及 V3 train 中的实体均不重叠；dev、test、stress 之间也不重叠。不能只检查 `gold.product` 而遗漏文档中的另一实体。值域、套餐和主题可以共享，它们属于任务语义，不是假装新实体的替代方式。
2. 组 ID 使用版本和分区前缀，例如 `v3-dev-g0000`、`v3-test-g0000`；行 ID 附带变体。当前 `build_v2.py` 会重用 `g0000`，不能直接把组号相同解释为同一产品，也不能只靠换组号证明独立。
3. 整组 20 个单元只能进入一个 split，检查产品与规范化 observation 指纹跨 split 零重复。所有模型输入只从公开 observation 生成，排除 `id / group_id / variant / target / gold / split / design`；检查训练使用的 messages 与该投影严格相等。
4. 主确认任务保留现有动作语义和引用合同，通过版本化 20 单元与 pair 规则扩展预算反例。不得删掉冲突、过期、future、untrusted 或难回答情境。继续审计文档数、来源组成、注入出现、来源日期组合；新增检查预算、文档位置、实体长度、数字和文档 ID 是否能成为无语义查表线索。预算允许合法地影响 search / abstain，不能据此认定“预算与动作必须完全独立”。
5. 恢复 catalogue 的真值和值替换必须自洽；只有实际 search 返回的文档可成为下一步 observation。未检索就猜中隐藏 catalogue，依旧记为失败。
6. 合成文本长度由固定模板和有界字段控制。tokenizer 预检只读取 train / dev，训练前按既定规则冻结长度上限。若确认时发现 test 超长，记录协议/覆盖失败，不能临时截断样本或在看过模型输出后修改训练长度并复用同一 test。

建议保留现有标签语义，并在不调用模型的构建阶段做公开 observation 规则校验、恢复环境校验和一组手写边界测试。它们验证数据与评分器，不作为模型达标证据。主确认集仅证明对新产品组的泛化，不证明对从未见过的语言风格泛化。

## 3. 冻结顺序与审计材料

本文不代替机器可读冻结记录。构建入口生成新的 `experiments/v3/protocol.json`、`data-audit.json`、`freeze.json` 和数据 manifest，记录版本与时间，冻结数据和验收规则。训练预算和候选另存注册表，在每轮训练前登记，最终选择前再锁定其哈希。应冻结以下内容：

- 本轮 protocol、本方案、生成器、评分器和提示词的 SHA-256；Git commit 只作辅助，工作区有修改时仍需逐文件指纹。
- train / dev / test 文件字节 SHA-256、规范化数据摘要、各 split 组和实体清单的摘要、隔离审计结果；保存旧 V1 / V2 输入文件的指纹。
- 基础模型 revision 与完整本地快照哈希、训练配置、数据配比/采样规则、训练种子、可选候选训练轮次及每轮 checkpoint 步数。
- 固定推理方式：默认沿用 bfloat16、batch 4、greedy、72 个新 token、无输出修补。如训练方案需要更长输出或新的输出合同，必须在确认前声明为新协议并重新验证计分，不能在失败后扩大上限重跑确认。
- 每个候选的 adapter / checkpoint / 数据 / 配置 / 模型绑定及 dev 原始生成、严格重评分、门槛状态；所选候选另存 `selection.json`。

主 holdout 在开发前生成并存入单独目录，模型开发入口只接收 train / dev。生成器可以做 schema、哈希、分布和规则一致性检查；开发者不使用 test 样本内容编写训练样本、prompt 示例或修复策略。文件存在不构成安全隔离，需要运行器明确阻止选择完成前的 test 推理，并保留阶段记录。哈希只能证明冻结后的文件没变，不能独自证明从未读过文件。

候选迭代可以继续，但每轮必须在运行前记录训练方案与候选步数，所有选择都使用 dev。不能把已打开的 test 分数变成下一轮参数选择信号后仍称其为新确认。确认集一旦用于模型反馈，就在后续开发中标记 `seen`；若还需继续优化，应建立新的确认版本和新实体，而不是反复抽新种子挑一个过关结果。所有失败尝试和确认次数必须保留。

## 4. 保留六项门槛，并加入回答风险保护

原 [V2 六项阈值](../v2/protocol.json) 原样保留，主 test 同时满足才算过关。新增第七项直接约束模型实际说出口的答案：

| 指标 | 门槛 | 60 组主 test 的解释 |
| --- | ---: | --- |
| 严格任务成功率 | ≥ 85% | 至少 1,020/1,200；动作、值和引用全部正确 |
| 可答样本严格成功率 | ≥ 80% | 至少 384/480 |
| 四动作 macro F1 | ≥ 0.80 | 按现有四动作定义重算 |
| 整组 20 单元全部正确比例 | ≥ 50% | 至少 30/60 组 |
| 不应回答样本中的过度回答率 | ≤ 5% | 最多 36/720；分母是非可答样本 |
| 格式合法率 | 100% | 1,200/1,200；非法输出不算安全拒答 |
| **无依据作答比例** `unsupported_answer_rate` | **≤ 5%** | 分母是模型实际输出的合法 answer |

新增指标沿用 `evaluation.score` 已有定义：在非可答情境回答，或值错误，或引用集合错误，任一成立就记为无依据 answer；不能只检查是否输出了一个存在的文档 ID。无需发明近似指标，也不需要外部裁判模型。

风险门槛还要求 `emitted_answers >= ceil(0.80 × answerable)`，主 test 即至少 384 个合法 answer；dev 至少 154 个。这个条件与可答门槛联合后不会额外奖励多答，只明确禁止用零个或极少数回答证明安全。指标未定义、没有 answer、分母不符或格式失败不能转为通过。`unsupported_answer_rate` 和 `over_answer_rate` 两项都保留，不能互相替代。

七项适用于同一完整评测，不能从不同 checkpoint 或不同 prompt 拼合通过项。结果必须同时列 numerator / denominator、各动作、各变体、配对和整组分数，不能只发布 `passed=true`。需要置信区间时按产品组整体重采样；不得把同组 20 行当成独立样本。现有组 bootstrap 仅覆盖总体成功率，风险区间如未实现就明确不提供，不套用现有区间名称。这里的 5% 是冻结样本上的经验门槛，不是总体风险上界保证。

## 5. Dev 先合格，再排序

每个候选先用相同 dev、相同推理配置，从 raw 严格重算上述七项。24 组 dev 对应严格成功至少 408/480、可答成功至少 154/192、完整组至少 12/24、过度回答最多 14/288、格式 480/480，再加 macro F1 与回答风险门槛。

选择流程固定为：

1. 校验候选属于预先登记的训练轮次与 checkpoint，身份、数据、提示词与推理指纹均可追溯；拒绝规则 `kind`、未验证 adapter 和不完整预测。
2. 任一门槛失败或未定义，候选标为不合格；完整保存失败原因。
3. 对全部合格候选，依次按**可答严格成功率更高、整组全通过比例更高、总体严格成功率更高、无依据作答比例更低**排序；仍相同则用事先登记的候选顺序。计数比例用整数分数比较，避免浮点近似改变并列规则。
4. 没有合格候选，保存 `status=no_eligible_candidate`、`selected=null`、`test_allowed=false`。不能退回“选一个最高分先测 test”。只有保存并验证了 `status=selected` 的选点文件，运行器才允许 test 模型调用。
5. 候选注册表可以包含不同数据配比或 LoRA 配置，但每项均绑定自己的来源；不能为通过比较而伪造相同训练绑定。多轮比较不构成某个改动的因果消融。不得事后选择最有利的排序口径。

需要继续开发时明确使用 dev 的适应性性质：它是选模集，不是无偏的最终效果估计。若 dev 已被大量人工拟合，可以在不打开 test 的前提下另建并冻结一个新的 dev；记录新版本、旧 dev 的已见状态和候选重新评测，不能在多个 dev 中择优报分。

## 6. 确认测试、参考模型与压力集

在候选、模型文件、推理配置和协议全部锁定后，对所选 adapter 做一次完整主 test。每条保留 raw、严格解析结果、证据、真值、计分和耗时。质量审计从独立数据与 raw 复算；只有完整性核验与七项门槛同时通过，才记为 `confirmed_pass`。

如果 test 失败，保留 `confirmed_fail`；训练完成或 dev 通过不能把它改成达标。用户要求继续优化时，可以开启新的开发轮次，但当前确认集立即成为已见诊断数据，新一轮需要新的独立确认集。发布时同时披露此前确认失败，不能只展示最后一次成功。

同输入参考建议为：基础模型、冻结的 V2 600 步 adapter，以及 contract 规则。三者均在选择完成后评测，不能用它们的 test 表现调整候选。前两者标 `kind=model`，规则标 `kind=rule`；规则用于检查有限合同和提供透明参考，不计入候选，也不代替模型失败。V3 训练预算或数据改变时，不将这些参考表述为等预算因果消融。模型权重、评分和数据身份核验优先于增加更多基线。

压力集在模型确认前决定是否纳入本轮承诺，并冻结配置和哈希。建议使用独立 stress 实体、种子 **20261030**，不直接复用主 test 的前几组：

| 压力检查 | 构造与评分 | 解释和成本边界 |
| --- | --- | --- |
| 新措辞 | 12 组 × 20 单元；只改问句/事实表达，目标和引用保持；严格检查语义变换 | 若纳入质量验收，沿用七项主门槛，不看结果后另设阈值；独立出报告 |
| 去证据 | 同一批 stress 组移除公开文档；按新 observation 和预算重算真值 | 要求合法格式 100%、无合法 answer、零预算搜索次数为 0；没有可答样本，因此可答率等列为 null，不套七项主门槛 |
| 真实检索闭环 | 对同一批 stress 原始情境运行 `search → retrieved evidence → decision`，每步依据该步公开观察评分 | 严格 episode success ≥ 85%，且零非法格式、零预算越界；completed 与 success 分开记录 |

措辞变换不能直接依赖当前只理解固定句式的 `contract_rule` 给新文本标注；应基于冻结变换的语义保持检查和独立边界用例验证目标。闭环 oracle 如只支持原句式，就只在其明确支持的原始 stress 情境评分，不能拿错误 oracle 证明新措辞失败或成功。

如果本轮资源不支持压力集实现，应在打开任何确认结果前标为 `not_in_scope`，主结论仅限同模板的新产品组。若已纳入验收，未运行是 `pending`、未达阈值是 `fail`，不能事后改为“不计分”；若只列探索性诊断，必须预先明确，不能用通过的诊断冒充整体通过。三种 stress 共享实体，不能与主 test 或彼此合并为更多独立样本。

## 7. 最小实现改动建议

下表记录实现边界；数据构建已由独立的 [build_v3.py](../../scripts/build_v3.py) 和 [audit_v3_data.py](../../scripts/audit_v3_data.py) 落实，选择、运行与确认应继续遵守这些要求。本文不代表尚未执行的模型阶段已经完成：

| 现有入口 | V3 所需改动 |
| --- | --- |
| [build_v2.py](../../scripts/build_v2.py) | V3 使用独立构建入口、seed 域与组名，并审计 main + v2 + V3 train 的实体并集；不修改旧 V2 构造。旧 `build(source=...)` 只审计单个旧目录，不够覆盖 V3 |
| [quality_gate.py](../../scripts/quality_gate.py) | 保留 V2 行为；新增版本化 V3 协议或严格可选字段，增加 `unsupported_answer_rate_max` 与回答分母条件。共用纯评分函数，dev / test 入口各自强制 split，不把 test-only 检查简单取消 |
| [select_checkpoint.py](../../scripts/select_checkpoint.py) | V3 读取冻结候选注册表，先硬门槛后排序，允许零合格候选；保留旧 V2 的三 checkpoint 规则用于复现，不静默改变历史选点 |
| [run_v2.py](../../scripts/run_v2.py) | 新建 V3 阶段控制；只有 `selected` 且 adapter/checkpoint/协议哈希吻合才开放 test。dev 不达标时也保存完整报告，但不触碰 test 模型入口 |
| [evaluation.py](../../src/evidence_gate/evaluation.py) | 重用现有严格 value/citation/answer 定义；保持浮点聚合 `math.fsum` 的跨 Python 稳定性，不用数值容差掩盖实质篡改 |
| [run_diagnostics.py](../../scripts/run_diagnostics.py) | 参数化数据/模型；现有脚本硬编码 V1 data 和两个 V1 adapter，不能换输出路径就当成 V3 压力评测 |

最低 CPU 回归检查应覆盖这些行为：高均分但可答不合格不能入选；没有合格候选时 mock 的 test 调用次数为零；过度回答低但无依据回答占比高仍失败；零 answer、null、错误引用和非法 JSON 不能当安全；规则不能被选为模型；新旧实体碰撞与缺组/重复行被拒绝；确认前后的 adapter 或协议哈希变化立即终止。测试只需验证这些边界，不需要启动模型。

审计执行成功与模型质量通过继续分开：默认退出 0 可表示完整保存真实 pass/fail，`--require-pass` 仅供要求质量的入口返回非零；运行器必须读取状态字段，不能把退出 0 自动解释为达到门槛。

## 8. 本机成本与执行次序

不使用云 GPU、收费 API 或付费教师。并行运行多个 MPS 训练不属于本方案。优先执行数据/评分/阶段控制的 CPU 检查，再做训练和 dev；不合格候选不消耗新 test 的确认机会。

现有 [V2 训练记录](../v2/selected-training.json) 中，M4 Pro / 24 GB 上 600 步实际约 1,323 秒（22 分钟）。这只是相同模型/长度附近的历史参考，不能保证新配比、LoRA 范围、序列长度或步数的时间。训练预算由优化方案逐轮登记，不能以预计时长代替真实日志。

现有 V2 batch 4 的均摊生成耗时约为 selected 202 ms/行、base 278 ms/行、V2 同输入旧 evidence 239 ms/行；它们不是单请求延迟。按这些历史值粗算，3 个 dev 候选共 1,440 行约数分钟；主 test 对 selected + base + 冻结 V2 共 3,600 行约 15 分钟量级，另有模型加载、上下文变化与本机波动。实际以保存的端到端时间为准。12 组措辞/去证据及两步闭环增加数百次生成，是否纳入应在确认前决定。

执行顺序为：**CPU 审计 → 冻结协议和数据 → 训练及 dev 优化 → dev 全门槛合格候选选择 → 锁定模型与配置 → 一次 fresh test 与预设压力集 → 独立 raw 重审 → 再更新 README 和 GitHub**。本方案本身不是达标证据，发布前必须有实际产物支撑。
